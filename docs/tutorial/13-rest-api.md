# Chapter 13 — REST API with DRF

## Goal

By the end of this chapter you'll have:

- A versioned REST API at `/api/v1/` covering Plans, Buckets, Tasks, Comments, and Notifications
- **JWT + Session authentication** working side-by-side: tokens for external clients, the existing browser cookie for the in-app browsable API and `fetch()`
- **Team-scoped permissions** that reuse the queryset-level `for_user()` filter we built in Chapter 6 — non-members get 404, never 403
- **Filtering** (`django-filter`), **search**, **ordering**, and **pagination** wired in once at the framework level
- **OpenAPI schema** at `/api/v1/schema/` and **Swagger UI** at `/api/v1/docs/`, generated by `drf-spectacular`
- A `config/api_router.py` aggregator that splices each app's API contributions onto a single URL surface

The big themes of this chapter: keep the *primary defense* in the queryset (not the permission class), let the *server* stamp creator/owner fields (never trust the client), and treat versioning as something you put in the URL once so views don't have to think about it.

---

## Why DRF (and not the JSON-rendering shortcuts)

Django can absolutely return JSON without DRF — `JsonResponse`, `serializers.serialize()`, hand-rolled `to_dict()` methods. We've used that pattern in earlier chapters for tiny endpoints (the bucket reorder JSON view in Chapter 9). It's the right tool for one-off dictionaries.

The moment you have a *resource* — a thing with a list endpoint, a detail endpoint, create/update/delete, validation rules, pagination, and a public schema — the cost of writing all of that by hand outpaces the cost of a dependency. DRF gives you:

- A serializer layer that's the same shape on read and write, with declarative validation
- ViewSets that map five HTTP verbs to five methods so you don't repeat yourself
- A pluggable auth/permission/filter pipeline that's identical across every endpoint
- A browsable API in dev that doubles as documentation while you're iterating

It's also a battle-tested ecosystem: `drf-spectacular` for OpenAPI, `djangorestframework-simplejwt` for tokens, `django-filter` for filter parameters. None of those are written by us, none of them go stale.

## Versioning

Three common approaches:

| Style | What clients send | Pros | Cons |
|---|---|---|---|
| **URL path** | `GET /api/v1/plans/` | Discoverable, easy to test by hand, easy to redirect when v2 ships | URL changes on version bump (intentional, but forces clients to update) |
| Accept header | `Accept: application/json; version=1` | URLs stay stable across versions | Hard to debug in a browser, easy to forget |
| Query parameter | `?version=1` | URLs stay stable | Mixes content-type and resource params; uncommon in 2026 |

We picked **URL path versioning**. For a tutorial it's the most legible, and in production it's the most operationally honest — it's clear from a log line *which* version a client hit, and a CDN/load balancer can route by path.

DRF supports it with one setting:

```python
REST_FRAMEWORK = {
    "DEFAULT_VERSIONING_CLASS": "rest_framework.versioning.URLPathVersioning",
    "DEFAULT_VERSION": "v1",
    "ALLOWED_VERSIONS": ("v1",),
    ...
}
```

The `v1` segment in `config/urls.py` is what `URLPathVersioning` reads to populate `request.version` — views that need to fork on version can check that attribute, but most don't have to.

## Authentication: JWT + Session, side-by-side

We accept *both* authentication classes. The order matters.

```python
"DEFAULT_AUTHENTICATION_CLASSES": (
    "rest_framework_simplejwt.authentication.JWTAuthentication",
    "rest_framework.authentication.SessionAuthentication",
),
```

**Why both?** Two distinct clients live in this app:

1. **The browser already logged in via the server-rendered side.** It carries a session cookie. Any in-app `fetch('/api/v1/plans/')` Just Works without the page having to manage a token. The browsable API at `/api/v1/docs/` also relies on this.
2. **External clients** (mobile, scripts, a future SPA on a different origin) don't share the session cookie. They `POST /api/v1/auth/token/` with `employee_id` + `password`, get back an access + refresh pair, and send `Authorization: Bearer …` on subsequent requests.

**Why JWT first?** When DRF returns a 401, it sets a `WWW-Authenticate` header by asking the *first* authentication class for its challenge. `SessionAuthentication` returns no challenge — so if it's first, unauthenticated requests come back as **403** instead of **401**. That's the wrong status code for an API: a missing/expired token isn't a forbidden action, it's an unauthenticated one. Putting JWT first gives you a clean `401 + WWW-Authenticate: Bearer` response.

### `simplejwt` and our custom user

Our `User` model uses `employee_id` as the primary key, not the default `id`. `simplejwt` defaults to `USER_ID_FIELD = "id"`, so without telling it about our PK it raises `AttributeError: 'User' object has no attribute 'id'` the first time it tries to encode a token. Two settings fix it:

```python
SIMPLE_JWT = {
    "ACCESS_TOKEN_LIFETIME": timedelta(minutes=15),
    "REFRESH_TOKEN_LIFETIME": timedelta(days=7),
    "AUTH_HEADER_TYPES": ("Bearer",),
    "USER_ID_FIELD": "employee_id",
    "USER_ID_CLAIM": "employee_id",
}
```

Short access tokens, longer refresh tokens — the standard pattern. If you later want logout-with-revocation, add `rest_framework_simplejwt.token_blacklist` to `INSTALLED_APPS` and run its migrations; we don't here because there's nothing yet that needs revocation.

## Permissions: keep the primary defense in the queryset

The cookbook DRF answer for "only members can see this" is to write a `BasePermission` subclass with `has_object_permission()`. That works, but it's the *second* line of defense. The first one is the queryset.

When `get_queryset()` returns `Plan.objects.for_user(request.user)`, three things happen for free:

- **List**: only the user's plans show up. No filtering needed in the view.
- **Retrieve**: a plan the user can't see returns `404` because the lookup falls through `get_object_or_404`-style. **404, not 403** — never leak the existence of a row a user shouldn't even know exists.
- **Update / Delete**: same deal. `self.get_object()` looks up against the scoped queryset, so a non-member can't `PATCH` what they can't see.

The permission class we declare is just the door bouncer: `permission_classes = [IsAuthenticated]`. That handles "you have to be logged in." Everything else is the queryset's job.

The team-scoping `for_user()` lives where the *data layer* knows about it (the QuerySet), so the API layer, the HTML view layer, and the admin all enforce the same rule the same way. There is no second copy of "what plans can this user see" sitting in a permission class waiting to drift.

## Project layout: per-app `api/` packages, one aggregator

Each app grows an `api/` package alongside the existing `views.py`, `urls.py`, `models.py`:

```
apps/plans/
  api/
    __init__.py
    serializers.py
    views.py
    urls.py
  models.py
  views.py     # the HTML views from earlier chapters
  urls.py      # the HTML urls from earlier chapters
```

This keeps API code separate from server-rendered code so they can evolve independently — but they share the same models, querysets, and signals. No duplication.

`config/api_router.py` is the single mount point. It does three things: it includes each app's `api/urls.py` flat under `/api/v1/`, it wires up the JWT obtain/refresh/verify endpoints, and it registers the schema + Swagger views.

```python
# config/api_router.py
from django.urls import include, path
from drf_spectacular.views import SpectacularAPIView, SpectacularSwaggerView
from rest_framework_simplejwt.views import (
    TokenObtainPairView, TokenRefreshView, TokenVerifyView,
)

urlpatterns = [
    path("", include("apps.accounts.api.urls")),
    path("", include("apps.plans.api.urls")),
    path("", include("apps.tasks.api.urls")),
    path("", include("apps.notifications.api.urls")),
    path("auth/token/", TokenObtainPairView.as_view(), name="token-obtain-pair"),
    path("auth/token/refresh/", TokenRefreshView.as_view(), name="token-refresh"),
    path("auth/token/verify/", TokenVerifyView.as_view(), name="token-verify"),
    path("schema/", SpectacularAPIView.as_view(), name="api-schema"),
    path("docs/", SpectacularSwaggerView.as_view(url_name="api-schema"), name="api-docs"),
]
```

Each app's `api/urls.py` builds its own `DefaultRouter` and registers its own ViewSets. The flat `path("", include(...))` means resources sit directly under `/api/v1/` (`/api/v1/plans/`, `/api/v1/tasks/`) rather than under per-app prefixes (`/api/v1/plans/plans/`). One namespace, owned by the router.

In `config/urls.py`:

```python
path("api/v1/", include("config.api_router")),
```

That's the only line that mentions `v1`. When v2 ships, you copy `api_router.py` to `api_router_v2.py`, swap whatever changed, and add a second mount.

## A representative ViewSet, end-to-end

Here's `PlanViewSet` in full:

```python
# apps/plans/api/views.py
class PlanViewSet(viewsets.ModelViewSet):
    queryset = Plan.objects.none()
    serializer_class = PlanSerializer
    permission_classes = [IsAuthenticated]
    filterset_fields = ["team", "visibility"]
    search_fields = ["title", "description"]
    ordering_fields = ["created_at", "modified_at", "title"]
    ordering = ["-created_at"]

    def get_queryset(self):
        return Plan.objects.for_user(self.request.user).select_related(
            "team", "owner", "created_by"
        )

    def perform_create(self, serializer):
        serializer.save(created_by=self.request.user)
```

A few things worth pulling out:

- **`queryset = Plan.objects.none()`** is for `drf-spectacular`. The schema generator has no `request.user` to plug into `for_user()` and would crash; the empty queryset is purely a type hint — the real per-request queryset comes from `get_queryset()`.
- **`select_related(...)`** keeps the list endpoint to a stable query count regardless of how many plans come back. Same N+1 hygiene we practiced in Chapter 9, applied at the API layer.
- **`perform_create()` stamps `created_by`** from the request user. The serializer marks `created_by` as read-only so even a malicious client posting `{"created_by": 999, ...}` gets the field overwritten by the server.

The serializer is plain `ModelSerializer` with one rule: anything the server controls is read-only.

```python
class PlanSerializer(serializers.ModelSerializer):
    class Meta:
        model = Plan
        fields = ["id", "title", "description", "team", "owner", "created_by",
                  "visibility", "created_at", "modified_at"]
        read_only_fields = ["id", "created_by", "created_at", "modified_at"]
```

> **Pattern: server-stamped fields are always read-only on the wire.** Without this, a client could spoof `created_by` to assign authorship to anyone. We've enforced it on `Plan.created_by`, `Task.created_by`, `Comment.created_by`, and `Bucket.position` — every "the server set this" field in the project.

## Filtering, search, ordering — wired in once

Three backends are configured globally:

```python
"DEFAULT_FILTER_BACKENDS": (
    "django_filters.rest_framework.DjangoFilterBackend",
    "rest_framework.filters.SearchFilter",
    "rest_framework.filters.OrderingFilter",
),
"DEFAULT_PAGINATION_CLASS": "rest_framework.pagination.PageNumberPagination",
"PAGE_SIZE": 25,
```

Each ViewSet then opts in by declaring fields:

```python
filterset_fields = ["bucket", "priority", "progress"]   # &bucket=4&progress=100
search_fields = ["title", "description"]                # ?search=login
ordering_fields = ["due_date", "priority", "created_at"] # ?ordering=-due_date
```

When the off-the-shelf field-equality matching isn't enough, write an explicit FilterSet. We did this for Tasks because the model doesn't have a direct FK to Plan, but clients want to ask "all tasks in plan X" without first looking up which buckets belong to which plan:

```python
# apps/tasks/api/filters.py
class TaskFilter(django_filters.FilterSet):
    plan = django_filters.NumberFilter(field_name="bucket__plan_id")
    assignee = django_filters.NumberFilter(field_name="assignments__user_id")

    class Meta:
        model = Task
        fields = ["bucket", "priority", "progress", "plan", "assignee"]
```

The `plan` filter walks `bucket → plan_id` under the hood. `assignee` walks the M2M through-table. From the client's perspective: `?plan=42&assignee=1003`. The query joins are the FilterSet's problem, not the caller's.

## Custom actions: read-only ViewSets with side-effecting endpoints

Notifications are a different shape. Clients don't *create* notifications — those come from signals and `django.tasks` (Chapter 12). The only mutation we need is "mark this read." That's a poor fit for `PATCH` (it doesn't update arbitrary fields), so we use a custom `@action`:

```python
class NotificationViewSet(viewsets.ReadOnlyModelViewSet):
    queryset = Notification.objects.none()
    serializer_class = NotificationSerializer
    permission_classes = [IsAuthenticated]

    def get_queryset(self):
        return Notification.objects.for_user(self.request.user).select_related(
            "actor", "target_content_type"
        )

    @action(detail=True, methods=["post"])
    def mark_read(self, request, pk=None):
        notification = self.get_object()
        notification.mark_read()
        return Response(NotificationSerializer(notification).data)

    @action(detail=False, methods=["post"])
    def mark_all_read(self, request):
        updated = self.get_queryset().mark_all_read()
        return Response({"updated": updated})
```

Two patterns to highlight:

- **`detail=True`** maps to `POST /api/v1/notifications/{pk}/mark_read/`. `self.get_object()` runs through `get_queryset()`, so a non-recipient gets a 404 when they try to mark someone else's notification read.
- **`detail=False`** maps to `POST /api/v1/notifications/mark_all_read/`. It's a *collection* action — no `pk` in the URL — and it dispatches a single `UPDATE … WHERE recipient = me AND read_at IS NULL` instead of N round-trips. The fat-queryset method `mark_all_read()` we wrote way back in Chapter 7 finally gets used.

`ReadOnlyModelViewSet` is what ensures `POST /api/v1/notifications/` and `DELETE /api/v1/notifications/{id}/` return 405 — the API surface stays narrow on purpose.

## OpenAPI schema and Swagger UI

`drf-spectacular` introspects every ViewSet and writes an OpenAPI 3 document. Two URLs come for free:

- `/api/v1/schema/` — the raw OpenAPI YAML/JSON (machine-readable; clients can codegen against it)
- `/api/v1/docs/` — Swagger UI rendered against that schema (human-readable; "Try it out" works against your live server)

### Helping spectacular help you

Three things we did to keep the schema clean:

1. **`queryset = Model.objects.none()` on every ViewSet.** Spectacular runs `get_queryset()` with no real `request.user`; if `get_queryset()` raises, spectacular falls back to "I don't know what model this is" and emits a warning. The empty class-level queryset is the type hint it needs.
2. **`@extend_schema(responses=UserSerializer)` on `MeView`.** Plain `APIView` doesn't carry a `serializer_class`, so we have to tell spectacular what comes back.
3. **Type hints on `SerializerMethodField` resolvers.** When the value comes from a method, spectacular can't introspect the return type. Add `-> str | None` (or whatever fits) and the schema gets the right type.

### Catching schema regressions

```bash
docker compose exec web uv run python manage.py spectacular --validate --fail-on-warn > /dev/null
echo $?   # 0 = clean schema, non-zero = warnings or errors
```

That's a single command for CI. Schema warnings are usually a missing type hint or a ViewSet without a queryset — small fixes that pay off forever once they're in place.

> **Add to `.gitlab-ci.yml`** — append a `validate` stage and a `schema` job to the bootstrap CI from Ch 3:
>
> ```yaml
> stages:
>   - lint
>   - test
>   - validate    # new
>
> schema:
>   stage: validate
>   script:
>     - uv run python manage.py spectacular --validate --fail-on-warn > /dev/null
> ```
>
> From this commit on, any PR that introduces a serializer field without a type hint, a `SerializerMethodField` without a return annotation, or a ViewSet missing `queryset = Model.objects.none()` goes red in CI before it ever reaches review.

## Testing the API

### Test layout mirrors the implementation

Earlier chapters had each app's tests as flat files: `test_models.py` for `models.py`, `test_querysets.py` for `querysets.py`, `test_views.py` for `views.py`. That works while everything fits in single modules.

Now that we've grown an `api/` *subpackage* with multiple modules (`views.py`, `serializers.py`, `filters.py`), the tests grow the same way. Instead of a single sprawling `tests/test_api.py`, we make a parallel `tests/test_api/` subpackage with one test module per implementation module:

```
apps/tasks/
  api/
    views.py
    serializers.py
    filters.py
  tests/
    test_api/
      __init__.py
      test_views.py        # ViewSet behavior — HTTP, scoping, 404s, custom actions
      test_serializers.py  # serializer-level checks — read-only fields, projections
      test_filters.py      # FilterSet wiring — query params produce the right rows
    test_models.py
    test_signals.py
```

**Why split.** Each test file stays focused on one piece of the implementation, so when a serializer field changes you grep `test_serializers.py`, not a thousand-line catch-all. New developers (and your future self) know where to add tests because the structure mirrors what they're looking at. The pattern scales: when we add `permissions.py` later, its tests live in `test_api/test_permissions.py` next to the others — no reorganization needed.

**Rule of thumb.** Whenever you add a new module under an implementation subpackage, add a matching test module under the parallel test subpackage. Don't merge multiple implementation files into one test file.

What goes in each kind of file:

| File | Tests |
|---|---|
| `test_views.py` | HTTP behavior — status codes, response shape, team scoping, server-stamped fields, custom `@action` endpoints, 405 on disallowed methods |
| `test_serializers.py` | Direct serializer assertions — `read_only_fields` declarations, `SerializerMethodField` outputs, computed fields, password/secret omissions |
| `test_filters.py` | FilterSet behavior — each query param narrows the queryset to the expected rows, including cross-model filters like `?plan=` walking `bucket__plan_id` |

Some checks could plausibly live in either file (e.g., "client-supplied `created_by` is ignored" — view test or serializer test?). The rule we settled on: if the test asserts about an HTTP request/response, it's a view test; if it asserts directly against a serializer instance or its fields, it's a serializer test.

### Writing the tests

DRF ships `APIClient`, a drop-in replacement for Django's test client that knows about content-types, format negotiation, and `force_authenticate()`:

```python
@pytest.fixture
def member_client():
    user = UserFactory()
    team = TeamFactory()
    MembershipFactory(team=team, user=user)
    client = APIClient()
    client.force_authenticate(user=user)
    return client, user, team


@pytest.mark.django_db
class TestPlanRetrieve:
    def test_member_can_retrieve(self, member_client):
        client, user, team = member_client
        plan = PlanFactory(team=team)

        response = client.get(f"/api/v1/plans/{plan.pk}/")

        assert response.status_code == 200
        assert response.data["title"] == plan.title

    def test_non_member_gets_404_not_403(self, member_client):
        client, user, team = member_client
        other_plan = PlanFactory(team=TeamFactory())

        response = client.get(f"/api/v1/plans/{other_plan.pk}/")

        assert response.status_code == 404
```

The **404 vs 403** test is the whole point — it asserts the queryset-level scoping pattern, not just the permission class. If someone refactors `get_queryset()` to skip `for_user()` and rely on a permission class instead, this test catches the difference.

We also test the JWT round-trip end-to-end:

```python
def test_jwt_auth_returns_current_user(self):
    user = UserFactory()
    user.set_password("secret-123!")
    user.save()

    client = APIClient()
    token_response = client.post(
        "/api/v1/auth/token/",
        {"employee_id": user.employee_id, "password": "secret-123!"},
        format="json",
    )
    access = token_response.data["access"]

    response = client.get(
        "/api/v1/me/",
        HTTP_AUTHORIZATION=f"Bearer {access}",
    )

    assert response.status_code == 200
    assert response.data["employee_id"] == user.employee_id
```

That single test exercises: the JWT obtain endpoint, our custom `USER_ID_FIELD` config, the JWT authentication class on a different request, and the `/me/` endpoint serializing the user it decoded from the bearer token. If any link in that chain breaks, this test goes red.

## What we didn't build (yet)

This chapter intentionally trims the API to the resources that demonstrate every pattern once. The following follow the same shape:

- **Label** — `LabelViewSet` filtered by `?plan=`, scoped by `for_user()`, same as Bucket
- **ChecklistItem** — same as Bucket, including auto-position on create
- **Assignment** — explicit M2M-through model; you'd expose it for write only (`POST` to assign, `DELETE` to unassign), no list/retrieve of its own
- **Attachment** — multipart upload + S3 storage; deserves its own chapter (Chapter 14 on search comes first)

Add them as exercises if you want to reinforce the pattern. The shared infrastructure (auth, permissions, pagination, schema) is already in place — each new resource is a serializer + a viewset + a urls registration.
